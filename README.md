# InsightFlow | FinTech Revenue Analytics

A payments analytics dashboard: it imports transaction and refund files, validates them with **Pandas**, stores them in **PostgreSQL**, and serves **SQL**-computed KPIs, revenue trends, refund analysis, a searchable transaction table, data-quality reports and explainable anomaly flags through a **FastAPI** backend, deployed on **Vercel**.

> The bundled dataset is **synthetic** (generated by `scripts/generate_sample_data.py`, 6 months, ~4.6k transactions) and is labelled "Demo data" in the UI. It deliberately contains bad rows and suspicious patterns so validation and anomaly detection have something to find.

## Features

- **KPI cards**: total transactions, GTV, refund amount, refund rate, net transaction value, net (fee) revenue, average transaction value, success rate. Each card shows its formula.
- **Revenue trend**: daily, weekly or monthly GTV, refunds and net value, zero-filled, with partial periods marked.
- **Breakdowns**: transactions by status, GTV by payment method.
- **Filters**: date range (presets + custom), merchant, payment method. Kept in the URL, so a refresh keeps the view.
- **Transactions table**: search by transaction/customer ID, status filter, sort, pagination, "flagged only". Click a row for the drill-down (refunds + anomaly flags).
- **Data quality**: every rejected row with its file, row number and reason.
- **Anomalies**: rule-based flags with a plain-English explanation per transaction.

## Architecture

```
CSV files ──► scripts/load_data.py ──► insightflow/validation.py (Pandas: clean + reject bad rows)
                                        insightflow/anomalies.py  (Pandas: rule-based flags)
                                        insightflow/pipeline.py   (COPY + INSERT … ON CONFLICT DO NOTHING)
                                              │
                                              ▼
                                   PostgreSQL (Neon in production)
                                              ▲
Browser ── public/ (HTML/CSS/JS + Chart.js, served by Vercel CDN)
   │  fetch /api/*                            │
   └──────────► app.py (FastAPI, a Vercel Python Function) ── insightflow/queries.py (SQL aggregation)
```

- **Pandas** handles the row-level work that is awkward in SQL: parsing messy text, per-row validation messages, rolling time windows for anomaly rules.
- **SQL** handles the aggregation (`SUM … FILTER`, `GROUP BY`, `date_trunc`, `generate_series`) so only small result sets leave the database. The API does not import Pandas, which keeps the serverless function small and cold starts fast.

## Metric definitions

| Metric | Formula |
|---|---|
| Total transactions | `COUNT(*)` of all attempts in the range, any status |
| Gross transaction value (GTV) | `SUM(amount) WHERE status = 'success'` (before refunds) |
| Refund amount | `SUM(refunds.amount)` for successful payments made in the range (attributed to the original payment date) |
| Net transaction value | `GTV − refund amount` (merchant money, **not** our revenue) |
| Fee revenue | `SUM(fee_amount) WHERE status = 'success'` (the platform's processing fee, UPI = 0) |
| Net revenue | `fee revenue − Σ ROUND(fee × refunded ÷ amount, 2)` (fees reversed pro-rata on refunds) |
| Refund rate | `refund amount ÷ GTV` (by value). Also shown by count: refunded payments ÷ successful payments |
| Average transaction value | `GTV ÷ successful payments` |
| Success rate | `successful ÷ (successful + failed)`; pending and cancelled are excluded |

Failed, pending and cancelled attempts count toward *Total transactions* but never toward GTV or revenue. Refunds are summed per transaction before joining, so a payment with several partial refunds is never double-counted. Timestamps are stored as UTC `timestamptz` and grouped into days in `REPORTING_TZ` (default `Asia/Kolkata`). Date ranges include both ends.

## Data validation (rows are rejected)

| Code | Rule |
|---|---|
| `MISSING_VALUE` | a required field is empty |
| `INVALID_AMOUNT` | amount is not a number or is ≤ 0 |
| `INVALID_FEE` | fee is negative or larger than the amount |
| `INVALID_TIMESTAMP` / `FUTURE_TIMESTAMP` | date can't be parsed / is in the future |
| `INVALID_STATUS`, `INVALID_PAYMENT_METHOD`, `INVALID_CURRENCY` | value outside the allowed set (after trimming and lower-casing) |
| `DUPLICATE_ROW` | exact repeat of an earlier row: one copy is kept |
| `DUPLICATE_ID_CONFLICT` | same `transaction_id` with different details: **all** versions rejected (we can't tell which is true) |
| `REFUND_UNKNOWN_TRANSACTION` | refund points at a transaction that doesn't exist |
| `REFUND_ON_UNSUCCESSFUL` | refund against a failed, pending or cancelled payment |
| `REFUND_BEFORE_PAYMENT` | refund dated before the payment |
| `REFUND_EXCEEDS_PAYMENT` | running total of refunds (including ones already in the DB) exceeds the payment |

Re-importing a file is safe: inserts use `ON CONFLICT DO NOTHING` on `transaction_id` / `refund_id`, and the whole import runs in one database transaction.

## Anomaly rules (rows are kept and flagged)

| Rule | Fires when | Severity |
|---|---|---|
| `POSSIBLE_DOUBLE_CHARGE` | same customer + merchant + amount succeeded twice within 2 minutes | high |
| `FAILED_ATTEMPT_BURST` | ≥ 3 failed attempts by one customer within 10 minutes (card testing) | high |
| `HIGH_VALUE` | amount ≥ 8× the merchant's median successful payment (merchants with ≥ 30 payments) | medium |
| `QUICK_FULL_REFUND` | fully refunded within 60 minutes of payment | low |

Thresholds are constants at the top of `insightflow/anomalies.py`.

## Project structure

```
app.py                      FastAPI app: routes, input validation, error handling (Vercel entrypoint)
insightflow/db.py           connection pool for serverless (lazy, small, PgBouncer-safe)
insightflow/queries.py      all dashboard SQL + KPI formulas
insightflow/validation.py   Pandas data-quality checks
insightflow/anomalies.py    Pandas anomaly rules
insightflow/pipeline.py     CSV → validate → COPY into Postgres → flag anomalies
db/schema.sql               tables, constraints, indexes
scripts/generate_sample_data.py   builds the synthetic dataset in data/
scripts/load_data.py        CLI to import CSVs
public/                     dashboard (index.html, styles.css, app.js)
tests/                      pytest: validation, anomalies, KPI hand-calculation, pipeline idempotency, API errors
```

## Run locally

```bash
python -m venv .venv && .venv/Scripts/activate        # macOS/Linux: source .venv/bin/activate
pip install -r requirements-dev.txt
docker run -d --name insightflow-pg -e POSTGRES_PASSWORD=devpass -e POSTGRES_DB=insightflow -p 5433:5432 postgres:17
cp .env.example .env   # set DATABASE_URL=postgresql://postgres:devpass@localhost:5433/insightflow
python scripts/load_data.py --reset
uvicorn app:app --reload   # http://127.0.0.1:8000  (API docs at /api/docs)
```

Tests (the KPI and pipeline tests need a throwaway database):

```bash
docker exec insightflow-pg createdb -U postgres insightflow_test
TEST_DATABASE_URL=postgresql://postgres:devpass@localhost:5433/insightflow_test pytest
```

## Deploy (Vercel + Neon)

1. Create a free Postgres database on [Neon](https://neon.tech). Copy the **pooled** connection string (host contains `-pooler`) and the direct one.
2. Load the data from your machine: put the direct string in `.env` as `DATABASE_URL_UNPOOLED` and run `python scripts/load_data.py --reset`.
3. Import the GitHub repo in Vercel. The FastAPI preset is detected from `app.py` + `requirements.txt`; no build command is needed. `public/` is served by the CDN.
4. In **Project Settings → Environment Variables** add `DATABASE_URL` (the pooled string) and, optionally, `REPORTING_TZ`.
5. Deploy and check `/api/health`.

**Why the pooled URL:** each serverless instance holds at most `DB_POOL_MAX` (default 3) connections, and Neon's PgBouncer multiplexes many instances onto a few Postgres connections. Server-side prepared statements are disabled (`prepare_threshold=None`) and the statement timeout is set with `SET LOCAL`, both of which are safe in transaction-pooling mode.

## Limitations

- Single currency (INR). No authentication: the dashboard is read-only and shows synthetic data only.
- Imports run from the CLI rather than through an upload page, which keeps write access off the public site.
- Transaction status is immutable after import: a later file that changes `pending → success` is ignored (`ON CONFLICT DO NOTHING`). A real system would upsert status transitions with an audit trail.
- Anomaly rules are fixed thresholds recomputed over the full history on each import. Fine for thousands of rows; at millions, they should be incremental, or computed in SQL with window functions.
- Refunds are attributed to the payment date (cohort view). A cash-flow view by refund date would be a second report.
